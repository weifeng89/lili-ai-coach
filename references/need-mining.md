# 需求挖掘细则（Phase A）

本文件是 `lili-ai-coach` 在 Phase A 的详细操作手册。面向 agent，中立第三人称。

## 1. 设计树（Design Tree）

把 lili酱 的想法展开成一棵「决策树」：每个决策向下挂出依赖它的子决策。

- 根节点 = 她想做的事（一个项目 / 一个功能）。
- 子节点 = 要定下来的具体决定（给谁用、在哪用、做成什么形态…）。
- 一个节点的答案会影响下游节点，所以**顺序很重要**。

## 2. Frontier 轮次（关键机制）

- **frontier** = 所有「前置依赖已定」的节点合集，也就是「现在就能问、不用猜还没问到的答案」的问题。
- 每轮把整个 frontier 一次性问出，**3–5 个**问题（比一次一个省轮次、比硬卡 3 个更问得清），每个编号（Q1…Q5）。
- 每个问题都给 **推荐答案**（agent 提，lili酱 选/改）。格式：

```
❓ Q1 - <问题标题>：<问题正文，可含几个选项>

➡️ 我的建议：<推荐选项 + 一句理由>
```

- lili酱 回答后，已定的节点把 frontier 向外推，解锁依赖它们的下游问题 → 重算 frontier → 下一轮。
- 答案依赖本轮另一个未答问题的，归属**下一轮**，不要本轮问。

## 3. 真伪需求探测（Real vs Fake Need）

对 lili酱 提出的每个「我想要 W」，**至少执行一次**反向追问：

> 「W 做成了，能帮你解决什么具体问题？」

判定：

| 结果 | 标签 | 处理 |
|---|---|---|
| W 直接对应一个具体任务，追问答得清 | ✅ 真需求 | 进入 PRD 的 T/C |
| W 只是手段，真正要的是更深的 N | ⚠️ 伪需求（手段） | 指出真需求 N，给**最小替代方案**（别顺着 W 做大） |
| 追问答不清 / 信息不足 | ❓ 待验证 | 记进完整度缺口，给出「如何验证」的建议 |

示例：
- lili酱：「我要个超酷的数据大屏。」→ 追问 → 「其实我就想每天看到自己学了多少小时。」→ 真需求 = 每日学习时长可视化；伪需求 = 大屏。最小替代：一个每日打卡 + 数字统计，而非大屏。
- lili酱：「做个日语助手。」→ 追问 → 「我想练听写，错的地方有人帮我标出来。」→ 真需求 = 听写 + 纠错高亮。

### 3.1 复述确认（硬性规则，防盲从）

标 **✅ 真需求**（以及 ⚠️ 伪需求对应的真需求 N）**之前**，agent 必须让 lili酱 **用自己的话把真需求复述一遍**，且复述需与 agent 推断一致，才算确认。

- 她说得清、且与推断一致 → 标记确认，进入 PRD。
- 她说不清，或复述跑偏（例如把"看学习时长"说成"做个好看的大屏"）→ **退回追问，不标记确认**，并温和指出差异："你刚说的是 X，我理解的真需求是 Y，咱们对一下？"

**为什么硬**：lili酱 缺乏技术判断力，容易"agent 说啥就是啥"而再次被带偏（这正是原 skill 的失效根因）。复述是让**她自己**当需求的最终裁判，而非 agent。

**示例**：
- agent 推断真需求 = 每日学习时长可视化；问"用你自己的话说说，你到底想要啥？"
- lili酱 复述："就是想每天打开能看到自己学没学、学多久。" → 与推断一致 → ✅ 确认。
- 若 lili酱 说："就是想要个很炫的页面。" → 不一致 → 退回，指出"炫页面是手段，你真正要的是'每天看到进度'"，重新对齐。

## 4. 事实归 agent，决定归 lili酱

- 凡能从环境/已给信息查到的「事实」（她已有啥工具、国产模型有哪些、是否需翻墙），**agent 自己查或基于已知给出**，不拿能自查的问题烦她。
- 只有「决定」（要 A 还是要 B、优先级）才抛给她，且带推荐。

## 5. 停止条件

- frontier 清空（每个分支都访问过，没有默默假设的东西），**或**
- 已收集到足够写一份 PTCF PRD 的信息（受 scope 护栏约束，见 SKILL.md Phase D）。

不要为「问得更全」无限发散。里程碑1 只服务 1 个项目。

## 6. Pattern 识别（跨轮抓真 / 伪需求）

逐问追问（§3）能挖单点，但 lili酱 常在多轮里**反复横跳、前后矛盾、或执着于某个「手段」却说不清为啥**。仅靠每轮 3–5 问不够——要用**跨轮 pattern** 把真/伪需求从对话整体里捞出来，避免「问了一堆却没捋清」，也避免她把前面说过的又忘掉。

**三类要盯的 pattern：**

| Pattern | 信号 | 处理 |
|---|---|---|
| ① 重复主题 | 不同轮次反复回到同一件事（如老提「大屏」「好看」） | 它不是偶发需求，是心结；优先追问其背后真目标 |
| ② 答案矛盾 | 这轮说「只在微信用」，下轮说「要独立 App」 | 指出矛盾，让她二选一并给推荐；不替她圆 |
| ③ 想要 W 说不清为啥 | 「我就要个超酷的 X」但问「做成了解决啥」答不上 | 直接标 **⚠️ 伪需求（手段）**，用最小替代把真需求逼出来 |

**为什么用 pattern 补 3–5 问：** 限制每轮问题数本是为防初学者被淹，但代价是「问得散、易忘」。pattern 识别让 agent 在**不增加单轮问题数**的前提下，靠回顾（压缩回顾见 SKILL.md Token 纪律）把散点连成判断，既省轮次又不易漏。

**示例：**
- lili酱 第 1 轮说「要个超酷数据大屏」，第 3 轮又提「页面要炫」→ pattern ①+③ 命中 → 标 ⚠️ 伪需求，追问出真需求「每天看到自己学没学」→ 最小替代：每日状态 + 数字，不做大屏。
- lili酱 第 2 轮说「在微信里用」，第 4 轮说「最好有个独立 App」→ pattern ② 命中 → agent 指出矛盾：「这两者有冲突，你更想要哪个？我的建议是先微信（零安装），跑顺了再考虑 App。」
